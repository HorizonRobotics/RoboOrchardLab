## 1. 只有三个函数会动通道

| 函数 | 位置 | 实测行为 |
|---|---|---|
| `ImageChannelFlip(output_channel=[2,1,0])` | 训练链与部署链各一次 | **【实测】** `(200,100,50) → (50,100,200)`,**恰好一次交换** |
| `data_preprocessor.process_img(channel_flip=True)` | 模型内部 | **【实测】** 同上,**恰好一次交换** |
| `deploy_policy.data_preprocess` 的 `[..., [2,1,0]]` | ⚠️ 仅评测侧,已删除 | 手写的第三次交换 |

**【代码】** `structure.py:245-247` —— `forward()` 在 `if self.training` **之前**调用
`data_preprocessor`,所以它在**训练与推理中同样生效**,不构成两侧差异。

## 4. 第 3 步凭什么说是 RGB

**【实测】** 训练解码后的数组与评测 `color` 的 `ch0/ch2`,两个任务各自独立:

| 任务 | 训练解码后 | 评测 `color` | 若两者通道相反应为 |
|---|---|---|---|
| cover_blocks | **1.55** | **1.49** | 0.65 |
| match_and_pick_from_conveyor | **0.92** | **0.92** | 1.09 |

⇒ **两个来源的通道排列相同。**(conveyor 那对尤其硬:0.92 与 1.09 相距足够远。)

**【实测】** 绝对方向的锚:场景材质 `Mahogany_Planks_BaseColor.png`(桃花心木)实测
**R=137.5 / B=29.3,R/B=4.69**,强烈偏红。渲染帧 `ch0/ch2 ≈ 1.5` 且 ch0 高 ——
**若 ch0 是 B,一个铺着红棕木料的场景会渲成蓝色调**,不成立。

⇒ **【推论】** 两个来源的 ch0 都是 R,即都是 **RGB**。

**一致性旁证**:训练侧两次交换互相抵消 ⇒ 模型收到的就是解码结果本身。只有当解码结果是
**RGB** 时,VLM 底座(在自然 RGB 上预训练)才拿到它期望的顺序。**管线在训练侧本来就是对的。**

## 5. 结论

```
训练      RGB → [img_channel_flip] → BGR → [channel_flip] → RGB      2 次 → 模型收到 RGB
评测(旧)  RGB → [deploy 交换] → BGR → [processor flip] → RGB
                              → [channel_flip] → BGR                 3 次 → 模型收到 BGR  ✗
评测(新)  RGB → [processor flip] → BGR → [channel_flip] → RGB        2 次 → 模型收到 RGB  ✓
```

**唯一的越界是 `deploy_policy.data_preprocess` 里那次手写交换。** 它在共享配置之外,
训练侧没有对应物。由 `xuewu.lin` 在首次提交 `057750be`(2026-07-22)写下,注释假设
「`cv2.imdecode` 给 BGR」—— 这个常识**对正常打包的数据成立**,但这份 LMDB 的解码结果是
RGB(第 4 节),所以在这里不成立。

⚠️ **该交换对其它数据集是对的**:若解码得到 BGR,评测三次交换的终点与训练两次交换的终点
一致。**受影响的只有「用这份 RoboDojo LMDB 训练 + 用这个策略包评测」的组合。**

## 6. 仍未查清的一件事

**这份 LMDB 是谁、用什么打的,我不知道**(在 `robot_lab2` 共享盘上,不是我们产出的)。
所以第 2 节第 1 步仍是猜测。它**不影响修复方向** —— 修复只依赖「两个来源排列相同」这个
实测事实 —— 但它决定「要不要修打包器 + 重打数据 + 重训」。要定死得问数据产出方。
