## 1. 失效模式的一般形式

### 1.1 「已声明未接线」（declared-but-unwired）

**定义**：一个配置面（键、开关、类、插件名）被定义、导出、甚至写进文档，
但**没有任何执行路径消费它**；系统沿另一条完全合法的默认分支运行。

**为什么不会崩**：缺少消费者**不是类型错误**。开关不存在时，读取方要么走默认值，
要么这段代码根本不存在——两种情况都是良构程序。编译器、类型检查、import 检查全部沉默，
因为「少一个引用」在语法和类型层面都合法。**唯一的症状是「设置它没有效果」**，
而这需要有人先怀疑它没效果才会去看。

**其他表现形式**（本次是第 1 种；2–4 为同类推广，标注可追溯性）：

1. **配置键无读取者** —— 本次实证：`episode_stream_sampler` 定义在
   `config_holobrain_common.py:59`，全仓零读取（`06e` §3.1 证据①）
2. **schema 加了字段，构造函数没转发** —— 本次实证：`_build_memoryvla_cfg()` 返回的 dict
   不含该键，`MemoryVLAMemory.__init__` 也没有该形参。**这一种最隐蔽**，
   因为 grep 键名能搜到「定义 + 表格 + 注释」共 5 处，看起来「有人用」
3. **类实现完整、导出齐全、但无人构造** —— 本次实证：
   `MemoryVLAEpisodeStreamBatchSampler` 零实例化（`06e` §3.1 证据②）
4. **开关穿过 N-1 层后在第 N 层被丢弃**（部分接线）—— **比完全不接线更危险**：
   grep 能找到若干读取者，「无消费者」这条判据会通过。（推测，本次未出现）
5. **注册名与查表名不一致**（注册器/插件机制里的拼写漂移）—— 注册成功、查找落空，
   查表方走 default 分支。（推测）
6. **CLI/env 解析进变量后无人引用**（推测）

**共同结构**：*定义点* 与 *消费点* 之间没有编译期或运行期的强制关联。
凡是这种关联靠「人记得去接」的地方，都是这一类的候选位置。

### 1.2 「验证装置补齐了被审对象的缺失」（harness-supplied integration）

**定义**：测试/验证脚本**自己构造了生产代码不构造的东西**，
于是 harness 跑的是一个**生产环境无法到达的配置**。测试通过，且通过得理直气壮。

**为什么不会崩**：harness 比生产**更完备**，不是更残缺。缺陷的形态是
「测试描述的不是将来会跑的那条路」，而不是「测试失败」。
更麻烦的是：harness 通常有**正当理由**这么做（本次 `run_gears.py` 文件头写明
「不走 `train.py`，因为 accelerate/checkpoint/logging 会引入不确定性」——**这个理由成立**），
所以这种偏离在代码评审里读起来像是审慎，不像是风险。

**其他表现形式**（本次同时命中 1、2、3 三种，见 `06f` §1）：

1. **harness 手工搭对象图，绕过生产工厂** —— 本次实证：`run_gears.py:138-145` 自行
   实例化 sampler，而生产入口 `train.py:124` 硬编码另一个
2. **harness 简化并发/并行** —— 本次实证：`num_workers=0`，于是「新字段扰动 worker
   随机流」这一失败模式**在结构上不可能发生**
3. **harness 用简化的优化器** —— 本次实证：`torch.optim.SGD(flat_list, lr=0.0)`，
   于是宿主真实的三组分组代码（`config_holobrain_common.py:528-556`）**一次都没执行过**
4. **fixture 预置了生产必须自己构建的状态**（预热缓存、预建目录、预填 DB）（推测）
5. **测试直接 import 模块，绕过生产的注册器/插件解析**（推测）
6. **单进程测试 vs 分布式生产**（推测；本次因单卡硬约束而无法验证 DDP，同一形态）

**共同结构**：**harness 与生产入口的每一处构造差异，都是一块未验证的表面。**
本次三处差异里，两处（worker、optimizer）查完是好的，一处（sampler）藏着 P0——
**事先分不清哪处藏着，所以三处都必须查**。

### 3.2 三次推翻的具体原因（这才是可带走的）

**C-v1 → 83 % 误报**：排除「定义文件」是想避免自引用，结果误杀了
`CrossTransformerBlock` / `GateFusion` / `TimestepEmbedder`——**它们在同一个模块里定义并构造**，
这是完全正常的写法。同时 `MemoryVLAMemory`（整个移植的入口类）也被误报，因为
配置驱动框架写的是 `dict(type=MemoryVLAMemory, ...)`，**从不出现 `Cls(`**。
→ **教训：任何「找死代码」的判据都必须同时理解「同文件构造」与「注册器间接构造」。**

**C-v2 → 漏报**：为解决上面第二点加了「裸名引用」正则，结果
`BottleneckSE` 与 `MemoryVLAEpisodeStreamBatchSampler` 被 **docstring 里的提及**
（`wrapper.py:33` 与 `:70`）判成「已使用」——**真正的 P0 被判为 ok**。
→ **教训：把误报换成漏报是净亏损。文本级判据在有文档的代码库上必然踩这个坑，
应当直接上 AST（字符串、注释、docstring 天然不是 `Name` 节点）。**

**F-v1 → 100 % 误报**：行级比对在**重新折行**面前全军覆没——
A 的 `scale = torch.sigmoid(self.proj(torch.cat([x1, x2], dim=-1)))` 一行，
移植后按 79 列拆成四行，于是「忠实拷贝」的相似度反而最低。
→ **教训：判据必须对「该忽略的差异」免疫。先把归一化目标想清楚（这里是格式），
再选比对粒度（字符级），否则判据本身成了噪声源。**

**cite 行号存在性 → 检出率 0**：本次 12 条漂移 cite **全部指向存在的行**
（漂移量 +1 到 +8，仍在文件范围内）。这条判据一次都不会响。
→ **不建议纳入。** 要机械化必须改 cite 约定本身：写 `path:符号名` 而非 `path:行号`，
再校验符号存在。这是流程变更，不是加一条检查。
佐证：本次指向 A 的**类定义行** 13/13 精确，指向块内中段行则大量漂移——
**符号锚点天然抗漂移**（`06a` §2）。

### 3.3 需要豁免机制的两条

**C** 与 **F** 都会在**合法情形**下响：

- `BottleneckSE` 被 C 判 UNUSED、被 F 判 DRIFT——它确实是「已移植但刻意不接入」
  且「刻意改写了方形网格假设」，两处都有文档。
- `PerMemBank` 被 F 判 ratio 0.105——A 里是逐参转发的 `__init__`，
  移植后直接靠继承，**行为等价但文本迥异**。

→ 两条判据都必须带 `--waive-*`，**且豁免列表本身就是产出**：
它是「这个移植在哪些地方停止做拷贝」的可审计清单。
**无豁免机制的判据会被使用者整体关掉，那就等于没有。**

## 4. 覆盖率反查：哪些通过项靠的是人工判断

### 4.1 靠人工判断但**可以机械化**（本次已补上工具）

| 通过项 | 本次怎么得出的 | 机械化形式 | 状态 |
|---|---|---|---|
| `CogMemBank` 与 A 逐行一致 | 人肉并排读 175 行（`06c` C 档小节） | **F 判据**，字符级 ratio 0.998 | ✅ 已实现并验证 |
| 68 个新张量全进 optimizer 正确分组 | 人工读 `build_optimizer` 推理 + 实测打印 | **O 判据** | ✅ 已实现 |
| 关闭态 batch key 不变 | 人工比对两次打印 | **B 判据** | ✅ 已实现 |
| 无原地操作 / 无硬编码 device | 人工设计 grep 模式 | 固化成 **S 判据**的扩展 | ✅ 已实现 |
| 「模块是不是摆设」 | 人工设计恒等探针 | **I/G/P 判据** | ✅ 已实现并双向验证 |

### 4.2 靠人工判断且**本质上不能机械化**（点名——这决定审查环节能不能裁掉）

1. **「本该搬什么」的清单**（`06b` §1 那 15 个方法要素）
   —— 必须读论文、把「动机 → 公式 → 输入 → 监督信号」拆开再定位到源码。
   机械判据只能验证「已经写下来的东西对不对」，**无法生成「本该有而完全没被提及的东西」**。
   本次的静默缺失（#15 episode 有序数据流）**正是从这张独立重建的清单里掉出来的**——
   若从 `01-source-anatomy.md` 的清单出发，它不会出现，因为那份清单也没有它。

2. **「声明不移植的理由是否成立」**
   —— `BottleneckSE` 不接入的理由是「压到 256 会破坏与 decoder 的 384 宽度契约」。
   判断这个理由成立，要同时理解 A 的动机与宿主的形状契约。**没有机械形式。**

3. **接口语义鸿沟的严重性**
   —— 「A 记 LLM 之前的视觉 patch，宿主记 VLM 之后已被语言条件化的特征，
   角色等价内容不等价」，这到底是「可接受的适配」还是「方法搬错了方向」。
   这是本次最深的一个问题，**任何检查器都答不了**。

4. **该对某个接口提出哪个问题**
   —— 「`uuid` 是 per-episode 还是 per-frame」一旦提出就是秒级可查的
   （若 per-frame 则 `hist` 恒空、记忆库退化——与 P0-1 同形），
   但**提出它需要一个「代码可能怎么错」的心智模型**。
   已提出的问题可以机械化；**提问本身不能**。

5. **harness 与生产的差异中，哪些差异要紧**
   —— 差异清单可以自动 diff（判据 X，推测可行），
   但「`num_workers=0` 只是简化、`sampler` 不同却是致命」需要判断。

> **结论**：把 §2 的 12 条判据全部落地后，能自动接管的是**取证**，不是**提问**。
> 4.2 的五项里没有一项能被裁掉，而它们恰恰产出了本次唯一的 P0 与唯一的方法论结论。
> 审查环节**不能裁掉**，但可以**变薄**：机械判据先跑，人工只处理它们的输出与 4.2 五问。

| **`copy_fidelity_check.py`** | 判据 F。按 `[port:]` 标记回源比对 | `--subdir --source-repo [--waive] [--min-ratio]` | ✅ 6 标记：4 个 ratio ≥ 0.998，2 个 DRIFT 均为已声明改写 |

按 (shape, dtype) 匹配进出张量，因此对「shape in = shape out」形状的移植模块通用
——而这正是移植协议本身要求的形状。

## 6. 排序

按「能拦住的失效严重度 × 复发概率 ÷ 单次成本」。

| 名次 | 判据 | 严重度 | 复发概率 | 成本 | 备注 |
|---|---|---|---|---|---|
| **1** | **K** 孤儿配置键 | P0 | 高 | 秒 | 本次 10 秒可查出 P0-1；0 FP |
| **2** | **I+G+P** 恒等探针三件套 | P0 | 高 | 分钟+GPU | 唯一能拦住「接线了但仍然无效」的判据 |
| **3** | **D** 默认值漂移 | P0 加重情节 | 中高 | 秒 | 与 K 从两个独立角度指向同一 bug |
| **4** | **F** 拷贝保真度 | P0（数值错） | 中 | 秒 | 拦「抄的时候手滑改了系数」，本次 C 档的静态平替 |
| **5** | **C** 无人构造的类 | P0 | 中 | 秒 | 与 K 互补：K 管键，C 管类 |
| 6 | **O** 参数全在 optimizer 内 | P1 | 中 | 免费 | 搭 I 的车，零边际成本 |
| 7 | **B** 关闭态 key 集合 | P0（污染） | 中 | 免费 | 搭 A 档的车 |
| 8 | **W** worker 流 | P0（污染） | 低 | 分钟+GPU | 需阳性对照，否则是假绿 |
| 9 | **S** 全局副作用 | P0 | 低 | 秒 | 本次 0 命中，但成本近零 |
| 10 | **X** harness/生产差异 | P1 | 高 | 分钟+GPU | **推测**，未实现；实现后应升到前 5 |
| — | cite 行号存在性 | — | — | 秒 | **不纳入**，检出率 0 |

### 如果只允许新增 3 条

**K（孤儿配置键）+ D（默认值漂移）+ I/G/P（恒等探针三件套）**

理由：

- **K 与 D 合计成本 < 10 秒、零误报，且从两个独立角度命中了本次唯一的 P0。**
  K 查「有没有人读」，D 查「文档说的默认值和 ship 的是不是一回事」——
  本次两条**各自独立**都能抓到，冗余是好事：任一条被绕过（比如键被某处虚假引用），
  另一条仍在。
- **I/G/P 是唯一覆盖「一般形式」而非「本次形态」的判据。**
  K 只能抓「键无人读」这一种表现形式；§1.1 列的另外五种（部分接线、注册名漂移、
  schema 未转发……）K 都可能漏。而恒等探针**不关心失效原因**，
  它直接问「开启之后，这个模块到底改变了什么吗」——
  任何原因导致的「开了等于没开」都会被它拦下。
- 三条一起构成「**便宜的静态筛 + 昂贵但兜底的运行时判据**」：
  日常每次提交跑 K/D（秒级），Gate B 之前跑一次 I/G/P（分钟级）。

不选 F 与 C 进前三的原因：两者都需要豁免机制才能用，而豁免机制本身要人维护；
在只能加三条的预算下，**优先选零维护成本的**。
